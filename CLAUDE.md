# ASCII Racer

A real 3D multiplayer driving game set in a city at night. It runs in the browser and is rendered entirely in ASCII characters. The scene is rendered in 3D on the GPU, then a shader pass converts it into a grid of text glyphs.

The night setting is the core of the look: darkness becomes empty cells, light becomes dense glyphs. Glowing street lamps, lit windows and neon draw the city, plus headlights, the only real lights.

## Stack

- TypeScript (game logic, input, physics, game loop)
- WebGL2 + GLSL (all rendering, including the ASCII conversion)
- Vite (dev server and build)
- No 3D libraries. The renderer is written from scratch.

## Architecture

Rendering happens in three GPU passes every frame:

1. **Scene pass**: draw the 3D world (streets, buildings, cars, lights) into a small offscreen framebuffer, `supersample` × `supersample` samples per cell. Outputs colour with the material ID in alpha, normals with the distance to the camera in alpha, and a scatter value (three render targets).
2. **Resolve pass** (`resolve.frag.glsl`): turns each cell's samples into one pixel per cell (`cells` target): the material covering most samples wins (ties to the centre), colour is the average of the covered samples dimmed by coverage (`coverageDimming`), normal, distance and scatter come from the winning sample. Thin and far things cover part of a cell instead of popping in and out.
3. **ASCII pass**: a full-screen fragment shader. Each screen pixel finds its character cell, samples the scene buffer at the cell center, picks a glyph from a ramp, and looks up that glyph's shape in a font atlas texture.

The ASCII conversion must stay on the GPU. Never read pixels back to JavaScript for per-frame work.

Planned layout (create folders as they are needed, not ahead of time):

```

```

### How it works today

- `main.ts` holds setup and the frame loop: pass 1 draws into the `scene` render target, the resolve pass into `cells`, the ASCII pass draws the full-screen triangle with `ascii.frag.glsl` (`asciiPasses`, the resolve and ASCII passes). Startup order: GL programs, glyph atlas, render targets and text grid, then one frame with the loading line on an empty scene (`drawLoadingFrame`, in a `requestAnimationFrame` callback), then a top-level `await` of a `setTimeout` so the browser presents that frame before the blocking `createWorld` and city meshes, then the state from the URL, the handlers and the frame loop. In headless Chrome the loading line is up 0.1–0.45 s after navigation (more with a cold shader cache) and the menu 0.6–0.95 s, 1.9 s and 2.7 s at 4× and 6× CPU throttling. `index.html` has a black background, so nothing white shows before it.
- The scene shaders are still named `triangle.vert.glsl` / `triangle.frag.glsl`. Each vertex is `x, y, z, r, g, b, nx, ny, nz, emission, id, material, facade u, facade v, facade seed, facade style` (`render/shapes.ts`: `box()` for axis-aligned boxes, `beam()` for bars at any angle, `disc()` for upright regular polygons such as octagon signs and round lamps, `facingBox()` for boxes facing ±x or ±z, `pixelArt()` for flat pixel letters and symbols drawn as one quad per run). `id` says which one a vertex belongs to, for things whose state changes: -1 for nothing special; `withId()` tags a shape, for now only traffic signal lamps. `material` (1–255) picks the glyph set; `withMaterial()` tags a shape. Materials are named in `render/materials.ts`, one glyph set (atlas row) each; a material's number is its place in the list plus 1. Matrices and fog are uniforms.
- Lighting is a dim ambient plus one directional "moonlight" on the per-vertex normals, so faces at different angles read as different brightnesses. Things that glow (bulbs, later windows and neon) use emission: at 1 the colour shows at full strength whatever the lighting. Glowing things don't light anything around them; per-light lighting for every lamp and window looked bad and doesn't scale. Only headlights (step 9) will be real lights.
- The ASCII pass draws each glyph in the cell's true colour, so dark surfaces get both sparser and darker glyphs.
- The scene pass clears with alpha 0 and objects write their material as alpha (`material / 255`, read back as `round(a * 255)`), so the ASCII pass can tell empty cells (drawn as solid background, no glyph) from objects and pick the material's atlas row.
- Fog uses the true distance to the camera (length of the view-space position, per pixel), so it is a circle around the camera. It is clear up to `fogStart`, then fades linearly to the background colour at the view distance, which is also the far plane (the fog circle always fits inside it). The background is black for now. The vertex shader takes `u_modelView` and `u_projection` separately so view space is available.
- Cells are `settings.cellWidth` CSS px wide and 1.75× as tall, times `devicePixelRatio`. The `cells` target has one pixel per cell (the `scene` target `supersample`² samples; `fwidth` in the scene shader is per sample, so it is scaled by `u_supersample` to get cells). Points (stars, particles) snap to cell centres and are `supersample` samples wide, so each is exactly one glyph, and the glyph atlas cells are exactly the cell size, so changing the cell size rebuilds the atlas.
- Windows (`render/models/facade.ts`, `facade()` in `triangle.frag.glsl`) aren't geometry. A wall is one quad whose corners count window bays and rows (`windowWall`, `glassStrip`), plus a seed and a `WindowStyle` (bay width, window size, lit share, `run` of bays lit together, sent as `u_windowStyles`), so a tower costs the same as a box. The scene shader picks wall, dark glass or lit window per cell and writes the `windowLit` / `windowDark` material over the wall's. Per axis, a window too small for wall around it fills its bay, and further away windows group into 2, 4, 8... so each group covers a cell (a street at a shallow angle keeps its rows). Dark glass turns back into wall once both axes are solid. Things that glow shine through part of the fog (`GLOW_THROUGH_FOG`), so the far skyline keeps its lights.
- Car model (`render/models/car.ts`): `carVertices(shape, color)` for the garage's `CAR_SHAPES` (`coupe`, `hatchback`, `pickup`, `van`, `wedge`; the ids are what is stored and later sent) and a `CarColor` (`render/models/palettes.ts`: `CAR_COLORS`, 12 named paints with an id, body and dark skirt, brightness 0.35–0.55; `carColor(id)` falls back to the first). Every shape is drawn from boxes, quads, `disc()` wheels and `prism()` (a convex side profile extruded across the car, a paint per rim face) inside the `CAR_WIDTH` × `CAR_LENGTH` collision box (light lenses stand `LIGHT_DEPTH` out of nose and tail), front towards -Z, at most `MAX_CAR_HEIGHT`, wheels at the same four spots (axles ±1.45 m) so `render/drift.ts`'s rear wheels fit every shape, the headlight origin (`render/headlights.ts`, middle of the nose) unchanged. The coupe with `ember` is the old car, vertex for vertex. Silhouettes, not details, tell them apart: coupe (hood, cabin, trunk), hatchback (short sloping hood, tall cabin to an upright hatch with a painted sill), pickup (tall cab, open bed with a dark floor between paint rails lower than the cab, bigger wheels), van (one tall box with a sloping windshield, cab and back-door windows), wedge (one slope from a thin nose to a high tail, small cabin, wing). Their cabins (`glassCabin`) are paint with the windows set in (`WINDOW_FRAME`, `PILLAR`), not all glass: glass facing away from the moonlight is nearly black, so an all-glass cabin left the roof floating over the body. The paint glows a little (`BODY_GLOW`) so the car reads from behind. Tail lights carry `BRAKE_ID` (-3) and are dimmed by the vertex shader unless `u_braking` (brake pedal held). Drawing only: nothing in `game/` knows the shape. `main.ts` rebuilds the car mesh whenever the stored choice changes (`updateCarMesh`).
- Garage (`app/garageMenu.ts`, `hud/garageScreen.ts`, `render/garage.ts`): the `garage` state from the menu's `garage` entry, Esc back to the menu with it selected. Rows `shape` and `colour` (`GARAGE_ROWS`); Up/Down (W/S) choose the row (`moveSelection`), Left/Right (A/D) cycle its choice, wrapping (`cycleChoice`), the pointer selects a row, a click on `<` or `>` steps it (`garageClick`, offsets `CHOICE_LESS` / `CHOICE_MORE`); every change is saved at once. `drawGarageScreen` draws `GARAGE` in the block font at the top and one framed panel at the bottom (the rows as `< coupe     >` with `>` `<` round the selected one, a hint line), so the middle stays clear for the car; smaller grids shrink the title, then a compact style (still fits 640 × 400 at glyph size 16); `garageLayout` (null when nothing fits), `garageRowAt` is the hit test; every cell once per call. The preview is its own small scene drawn instead of the city (and gates): the player's car at the origin turning left once per `GARAGE_TURN_TICKS` (16 s, `garageHeading` of the fractional tick), on a glowing floor in its own `garageFloor` set (dots to rings): bright out to `SPOT_INNER_RADIUS` round the car, then fading to the dark at `SPOT_RADIUS` (`flatDisc` with a rim colour plus `flatRing`), seen from `GARAGE_CAMERA` (5.6 m away, 2.8 m up, looking a little under the car's middle), under the garage's own light (`GARAGE_LIGHT_DIRECTION` from above the camera's side, `GARAGE_AMBIENT`, `GARAGE_LIGHT_INTENSITY`) instead of the moonlight; headlights off, no HUD, stars still drawn. `world.car` is not touched (it stays where the menu stood it) and the world keeps ticking.
- Beacons: `BEACON_ID` (-2) dims with `u_beaconOn`, which `main.ts` sets from the tick, so all rooftop masts blink together.
- Glyph sets (`render/materials.ts`): each is a 10-glyph brightness `ramp` (darkest first) plus optional `edges` (dim, left, right). An atlas row is ramp + edges, blanks when a set has none. `EDGE_MATERIALS` is a bitmask uniform of materials with edges (only materials 1–31 can have them).
- Edge glyphs: a cell whose left or right neighbour is empty or faces another way (normals more than ~25° apart) is the left or right edge of its face and gets `[` / `]` (dim cells `|`). Only from `EDGE_MIN_LEVEL` up, so fogged far buildings don't turn into rows of edges. The normals target's alpha holds `sqrt(distance / view distance)` (8 bits, finer up close); a neighbour more than `EDGE_DEPTH_STEPS` closer is in front (a pole before a wall) and doesn't make an edge. Top and bottom edges (`‾` / `_`) were tried and dropped: far buildings are only a few rows tall and turned into thin lines.
- Animated sets (`animated: true`, bitmask `ANIMATED_MATERIALS`): the ASCII pass moves the level up and down by two crossing sine waves of time and screen cell (`u_animationPhase` = tick within the loop, 0–1). Waves in world space were tried and dropped: too uniform. Shore cells (a neighbour is another material and not in front) splash to the top of the ramp, picked by a hash of cell and time slot. `u_tick` is sent as an int, which stays exact (the no-tick-on-the-GPU rule is about floats). Settings on the dev menu's Animation page.
- Scatter sets (`scatter: { square, patch, patchiness }`, bitmask `SCATTER_MATERIALS`): the glyph is picked by a random value instead of brightness; level 0 still stays empty and the glyph still takes the cell's colour. The scene pass computes it from the world position on the surface's own axes: a hash per grid square (squares double per axis further away until each covers a cell, so far ground doesn't reshuffle every frame) mixed with value noise patches, the material number in the hash so each set has its own pattern, settings per material in the `u_scatterParams` array. It goes to the ASCII pass in the third render target (R8). Defaults in `materials.ts`, edited on the dev menu's Scatter page. Tried and dropped: brightness picking a window of the scatter string.
- Stroke sets (`strokes: true`, bitmask `STROKE_MATERIALS`): on faces that slope on screen, the glyph comes from one of four stroke sets (`strokeVertical`, `strokeBackslash`, `strokeHorizontal`, `strokeSlash`, plain ramps that must stay in that order from `STROKE_ROW`) instead of the material's ramp. The ASCII pass rotates the face's fall line (straight downhill on the face, from the world normal) into view space with `u_viewRotation` and bins its on-screen angle (`STROKE_VERTICAL_RANGE`, `STROKE_HORIZONTAL_RANGE`). Flat faces (`FLAT_NORMAL_Y`) and fall lines pointing at the camera (`STROKE_MIN_LEAN`) keep the ramp; edge glyphs win. House roofs and the pointed tower tops (`houseRoof`) use it; tried on all building walls and dropped. The ScreenNormals render mode shows the view-space normal.
- Weather (rain and snow as a screen-space overlay in the ASCII pass, wet roads as an animated set) was tried and dropped: an overlay doesn't move with the camera and has no depth, so it never looked like it was in the world. A second try (drops on rings around the camera, hidden by nearer scene, leaning in a wind) was dropped too: rain looked like hyperspace and snow drew curved bands.
- World clock (`game/clock.ts`): the simulation counts fixed ticks at 60 per second (`advanceClock` runs one step per whole tick in the frame time and carries the rest over). Anything that changes over time in the simulation reads the tick, never frame time or the browser clock, so it is the same on every machine and in replays. It is world time, not race time: it starts when the city loads, and game modes record their start tick. The frame time is capped at 0.1 s (`capFrameSeconds`), so a slow frame never runs more than 6 ticks.
- World (`game/world.ts`): the simulation without WebGL or DOM, so it runs in Node (tests, later a server). `createWorld(citySettings, carSettings)` generates everything from the seed (city, layout, fences, driveways, street furniture, signal offsets, models and every collider) plus the car at tick 0, standing on the middle junction (`startJunction`); the settings are kept by reference, so dev menu edits apply. `stepWorld(world, input)` runs exactly one tick (car step, collisions, tick count), keeps `previousCar` for drawing between ticks and returns the `Impact` for crash debris. `regenerateCity` rebuilds the city from the current settings, keeping car and tick. `generateCityData(settings, false)` builds everything but vertices: `withoutVertices` (`render/shapes.ts`) makes every shape return none, so models make the same random calls and colliders in about 1% of the time. `main.ts` reads the keyboard and calls `stepWorld` once per tick from `advanceClock`; it keeps meshes, particles, cameras and the dev menu, and reads `world.tick` for anything drawn from the tick.
- Reference run (`game/referenceRun.ts`, `game/determinism.test.ts`): a seeded script of inputs held for random stretches drives 10 000 ticks; FNV-1a over the exact bytes of the car state (sampled along the run), every impact and a digest of the generated city (colliders, buildings, junctions, signal offsets) gives one hash per seed. If it fails, simulation or generation changed: only fine on purpose, then replace the stored hashes by hand and bump `SIMULATION_VERSION` (below). Simulation and generation code must use `math/deterministic.ts`, never `Math.sin`, `Math.hypot` and the like.
- Simulation version (`game/version.ts`, `game/referenceValues.ts`, `game/version.test.ts`): `SIMULATION_VERSION` (positive integer, 1 now) is stored with every run later and checked by the server; it is bumped by any change that can alter what a city seed, route seed and input log produce (generation, routes, daily derivation, physics, collisions, race rules, the input log's meaning). The stored values that define that (`REFERENCE_HASHES`, `DRIVEN_RACE_HASH`, `PACKED_RACE_HASH`, `REFERENCE_ROUTES`, `REFERENCE_SEEDS`, `REFERENCE_RACES`) live in `referenceValues.ts`, each test reads its value from there. `version.test.ts` hashes them with `INPUT_LOG_VERSION` into a fingerprint and compares it with `SIMULATION_FINGERPRINTS[SIMULATION_VERSION]`; it also needs versions 1..current with no gaps and no fingerprint used twice (a bump with no change in the values is refused). Procedure for an intentional change: the reference tests fail, replace the values in `referenceValues.ts`, bump `SIMULATION_VERSION`, add the fingerprint the version test prints (keep old entries), and deploy together with the server. The test driver's tuning and the shot spots are not in the fingerprint.
- City rules (`game/cityRules.test.ts`): seeds 1–200 with the default settings, built without vertices. Nothing solid on a road (bounds minus blocks; car parks and driveways are inside blocks), every junction reachable from the start along car-wide corridors down the road centres, no way out past the outer wall (flood fill of the car's centre on a 0.5 m grid, colliders grown by the car's radius), no prop inside a building collider or overlapping another prop (except one standing in another, and fences meeting), start on a road and clear. Building models' colliders carry `building: true` (set in `cityModels`) so props can be told apart; nothing else reads it.
- Collisions (`game/collision.ts`): everything solid is a `Collider` (footprint `rect` seen from above, plus `top`). `cityColliders` collects buildings and the poles of street lights, traffic lights and stop signs; arms, signal heads and signs hang overhead and don't collide. Pole sizes are exported from the `game/` files and imported by the models, so drawn and solid poles always match. A circle is pushed out of each rectangle (`pushOutOfRect`); colliders whose top is below it are skipped, so the fly camera can pass over. The car (`collideCar` in `game/car.ts`, ignoring `top`) is a capsule as wide as it, round ends at nose and tail: for each rectangle the circle at the centre line's point nearest it is pushed out. `stepWorld` passes the position before the tick's move, which is walked in steps of at most `MAX_COLLISION_STEP` (0.1 m), each pushed clear in up to `COLLISION_PASSES` passes over the colliders near the move; the pushes add up to the impact's normal. Seams: where the nearest point lies past a rectangle's corner and a neighbour covers the spot just past that corner along one face (within `SEAM_GAP`, 1 mm) but not along the other, the rectangle is stretched over that neighbour first, so a flat wall cut into several colliders pushes straight out exactly like one rectangle instead of off the joint's corner (`wallSeam.test.ts`: cut walls and inside corners match bit-exactly, a cut outside corner within 1e-9). Tried and dropped: three circles resolved once at the end of the tick. A fast sideways slide skipped a pole past a circle or squeezed the car through the exactly car-wide gap between a street light and the building, and the pole hooked into the notch between two circles, holding the car for half a minute or more (collisions never turn the car). A convex capsule pressed between a pole and a wall can always slide out along its length one way.
- The camera is a position plus yaw and pitch (`render/camera.ts`). `game/input.ts` tracks held keys (by `event.code`) and pointer-locked mouse movement; `game/flyCamera.ts` moves the camera each frame using the frame time `dt`. The fly camera is a dev tool, not simulation, so it does not use the fixed timestep.
- Runtime settings (FOV, cell width, view distance, fog start, render mode, ambient and directional light) live in a `DevSettings` object edited by the dev menu (`dev/menu.ts`, backtick key). The dev menu is plain HTML on top of the canvas; that is fine because it is developer UI, not the game picture.
- Text layer (`hud/`): HUD and menus are text in the glyph grid, not HTML. `TextGrid` (`hud/textGrid.ts`, no WebGL) is a terminal: `put`, `write` (with `color` 0xRRGGBB, `background`, `align` left/right/center around the given column), `fill`, `box` (a `+-|` frame with a solid inside), `clear`, `resize`. Negative columns and rows count from the right and bottom (-1 is the last); anything off the grid is clipped, characters outside 0x20–0x7E become `?`. Each cell is 4 bytes: the character code (0 = nothing) plus 128 for a solid background, then red, green, blue. `dirty` is set only when a write changes a cell, so redrawing the same text every frame costs no upload. The grid covers only whole cells (`floor` of the canvas over the cell size), its row 0 the highest whole row of the scene's cells, so it shares their grid and nothing is cut off at the top or right; `main.ts` resizes it with the render targets (which clears it). `hud/hudTexture.ts` uploads it as an RGBA8UI texture (texel row 0 = grid row 0) with `texSubImage2D`, only when dirty. The printable characters are atlas rows after the material rows, cut to the same width (`printableRows`, 13 per row), so one atlas holds both and they rebuild together. In glyph mode (and CRT glyphs, which blurs it like everything else) the ASCII pass draws a cell's character in its colour on the background colour instead of the scene's glyph, untouched by fog, edges and animation; a space or code 0 shows the scene unless the cell has a solid background. Other render modes don't show it.

- Driving HUD (`hud/hud.ts`): `drawHud(grid, { speed, topSpeed })` draws the speedometer panel in the bottom right corner: the speed as three right-aligned block digits (3×5 cells of `#`, leading positions blank), `km/h` under them, and a bar against the car's top speed setting, in a dim frame with a solid background. The panel has a fixed size and every cell of it is written exactly once per call, so drawing the same values again leaves `dirty` unset; it is not drawn at all when the grid is too small for it. `main.ts` calls it every frame in the race state with the car camera, with the magnitude of the drawn car's velocity (sliding and reversing included), and clears the grid in the fly camera. The minimap is in the bottom left, the race elements at the top.
- Minimap (`hud/minimap.ts`, bottom left, drawn by `drawHud` when given `minimap`): the whole city, north (-Z) up, laid out from the road lines rather than scaled: every road line is exactly one cell and every block the scale's cells, so roads never vanish or double and a square city stays nearly square with tall cells. Scales (`MINIMAP_SCALES`, largest first): 5 × 2, 3 × 1, 2 × 1, 1 × 1 cells per block; `chooseMinimapScale(blocks, rows, maxWidth, allowed)` keeps the scales at most `maxWidth` wide that `allowed(width, height)` accepts, takes the first (largest; of equal heights the larger scale comes first) whose framed panel is at most `MINIMAP_MAX_HEIGHT_SHARE` (0.45, so the default city keeps 5 × 2 from 65 rows up, e.g. 1280 × 720 at the default cell width) of the grid's rows, else the first of them (the largest), else null (no map). `drawHud` allows a scale only if the map stays clear of where the race timer goes (the timer's rectangle, reserved in free driving and on screens without a timer too, when the timer fits the grid and clear of the speedometer), so a map never costs the player the timer; `drawPreRaceScreen` only if the text's smallest style keeps its place (`mapFitsPreRace`). A 10 × 10 city is 3 × 1 at 213 × 68 and 5 × 2 from about 78 rows. `fitMinimap(minimap, rows, maxWidth, allowed)` (returns whether any scale fits, no map is drawn when not; called by `drawHud` with the room beside the speedometer and by `drawPreRaceScreen`) swaps `minimap.layout` when the scale changes and forgets what was drawn, so the next draw writes the whole panel (`drawn.layout` is part of the intact check); the grid is cleared by the resize that causes it. `minimapLayout(city, scale = 5 × 2)` builds it from the blocks and `bounds` (default city at 5 × 2: 49 × 25 cells, 55 × 29 with frame and padding); streets `- | +`, avenues brighter `= H #`. `minimapPosition(layout, x, z)` maps world to fractional map cells piecewise linearly (a road's width to its cell, a block's to its cells, clamped to the map), `minimapCell` rounds it: for later routes, gates and other cars. The car is one cell (`A < V >` by heading; `^ v` were too small to find). A `Minimap` remembers what it drew: a frame only restores the cell the car left and draws the car, unless the grid, its size or the frame's corner changed (cleared). Not drawn unless it fits beside the speedometer with a margin. `main.ts` rebuilds it with the city.
- Race HUD (`hud/raceHud.ts`, `hud/guidance.ts`, drawn by `drawHud` when given `race`; `main.ts` passes it in the race state whenever `world.race` exists, so `race=0` draws exactly the old HUD): three elements, each a fixed rectangle that writes every cell once per call (see-through blanks when it has nothing to show), so the same state leaves the grid clean. The centre column under the timer stays clear while racing, so the next gate's beam straight ahead is never covered. The timer panel, top centre (35 × 7): `raceTicks` as `m:ss.mmm` in the block font (`hud/blockFont.ts`, 3×5 `#` characters shared with the speedometer; one minutes digit, capped at 9:59.983), `0:00.000` in the countdown, frozen after the finish, with `GATE  3/12` in its bottom frame line (gates passed over all gates, the finish included). The guidance a column to its right, same rows, from `routeGuidance(graph, race, car)` with the camera's yaw as heading. - Game states (`app/gameState.ts`, `app/flow.ts`): app flow, not simulation, so nothing of it is in `World` or the hashes. A `GameState` is plain data: `menu` (holding the selected entry), `preRace` (the daily's: day and route), `race` (unlimited: its route, null only for the URL's free driving; daily: day, route, `givingUp`, `finished` time or null), `results` (unlimited's: the route, the time in ticks and the selected option), `dailyResults` (day, time or null for did not finish, selected entry), each race one with its `RaceMode` (`unlimited`, `daily`; lobby joins the type), `settings` (the selected row and the nickname being typed, below) and `garage` (the selected row, above) and `loading` (unlimited: a new city and route being made; daily: the day's city being built for its route). Unlimited (`flow.ts`): `randomCitySeed()` (1 to `UNLIMITED_SEEDS`, `Math.random`: app flow, the one place it is right), `seedRoute(settings, seed)` (the route of the seed's city with route seed = city seed, from `generateCity` and the road graph only, so a failing seed costs no buildings), `unlimitedRoute(pickSeed, routeFor)` (skips seeds that throw `RouteError`, null after `UNLIMITED_TRIES`). `main.ts`'s `newUnlimitedRoute` writes the found seed into `citySettings` (the object the dev menu edits) and calls `loadCity(citySettings)`, which rebuilds the world's city data, meshes, signal texture, minimap and flight (about 0.5 s in headless Chrome). The dev menu's regenerate stays synchronous: `loadCity(citySettings)` plus the menu. `loadCity(settings)` sets `world.citySettings` to the object it builds from (the dev menu's info line shows its seed) and remembers it as JSON (`builtCity`), so the daily can tell whether its city is the one built. `main.ts` reads the car's input only in the race state, clears the text layer on every change and draws the state's screen: the main menu, the finish screen and the daily's screens (below), each writing the same cells every call, the driving and race HUD only while racing. The fly camera is chosen only on the dev menu (Movement), works in every state and hides the text layer as before. Regenerating the city goes back to the menu.

- Sound (`audio/`, step 18; reads the game, never feeds back into it, nothing in `game/` knows it): `createAudio(makeContext, tuning)` (`audio/audio.ts`) owns the one `AudioContext`, typed through small `*Like` interfaces so tests use a fake. Graph: sources -> a bus (`GainNode`; `world` and `interface` exist from the start, `bus(name)` makes more) -> master `GainNode` -> limiter (`DynamicsCompressor`, -6 dB threshold, ratio 12, so layered sounds can't clip) -> destination, with an `AnalyserNode` after the limiter. `audio.context()` is the context only while it is running and its clock has started (`currentTime > 0`): Chrome reports `running` at construction while the clock stands still until the output device starts (a Bluetooth output can take over a second), and anything scheduled then would play bunched at 0.01 s, so one-shots (race sounds, thuds, the blip) and the continuous sounds' per-frame updates and retunes are skipped in that gap (dropped, never queued); the master gain (`setLevels`, `retune`, the hidden fade) uses the raw context and applies at once. Start rule: `installGestureStart` listens (capture phase, before any screen's own handler can stop the event) for `keydown`, `pointerup` and `click` on `window` and calls `audio.start()`: the first creates the context, later ones `resume()` a suspended one, none does anything while it runs. Before the first gesture there is no context and every call (`setLevels`, `blip`, `bus` -> null, `retune`) is a no-op; nothing is queued, so no catch-up sounds. `whenReady(cb)` runs `cb(audio, context)` once when the graph first exists (the context even while still suspended): where later sounds build their sources and connect them to a bus. Count nodes you make with `audio.counted(node)` and call `audio.released(n)` when they are disconnected for good (the stats' `nodes` must stay flat; one-shots free themselves in `onended`). Without `AudioContext`, or under `shot` / `tick` (`main.ts` passes no factory), the game runs silent and no context is ever made. Volume: `masterGain(volume, muted, tuning)` (`audio/gain.ts`) is exactly 0 when muted or at step 0, `topGain * (volume / VOLUME_STEPS) ^ volumeCurve` between (curve 1.5: steps 1 to 10 give 0.032, 0.089, 0.164, 0.253, 0.354, 0.465, 0.586, 0.716, 0.854, 1), exactly `topGain` at 10; applied with `setTargetAtTime` (5 ms time constant) from `storePlayerSettings` and at startup. `shouldBlip(previous, next, tuning)`: a volume or mute change that ends audible plays `audio.blip()` (60 ms sine, `blipHertz`, through the `interface` bus), from `applySettingsChange`. `audio/tuning.ts` holds the numbers to tune by ear (`AudioTuning`: curve, top gain, `busGains` by bus name, blip gain and pitch); the dev menu's Sound page edits that object (sliders call `audio.retune`) and shows the context state, master gain, node count and the output's RMS and peak in dB (100 ms refresh while open). Later sub-steps add their constants to `AudioTuning`, their sliders to that page and their sources to a bus. Hidden tab: the frame loop stops while the tab is hidden, so `installVisibility(document, audio)` calls `audio.setHidden` on `visibilitychange` and the master fades to 0 (20 ms time constant) until it is shown again; every continuous sound is covered by it. Engine (`audio/engine.ts`): `buildEngine` (from `createEngine` in `whenReady`, 14 nodes, 19 in the graph with it, all `counted`, started once and never stopped): a sawtooth `detuneCents` (7) up and a square 7 down at the note, a sine an octave below, 2 s of seeded white noise looped through a band-pass at `noiseBand` × the note, all into a resonant low-pass (`resonance` Q 5 dB) -> a level gain -> a high-pass (`highpassHertz` 40: nothing below it reaches the bus, small speakers don't play it and infrasound eats limiter headroom) -> the `world` bus, plus a sine LFO (`wobbleHertz` 4.5) on every oscillator's detune. `engineSound(input, tuning, out)` is pure (writes into `out`, no allocation): from the signed speed (`engineSpeed`: the whole speed, so a slide keeps the revs, negative when the car moves tail first), the car's top speed, throttle and brake (0 when the game reads no input: outside the race state and in the countdown) and the previous gear it gives `gear`, `hertz`, `level`, `cutoff`, `noise`, `wobble`. Gears (`engineGear`): five, by share of top speed (`gearTops` 0.2, 0.38, 0.57, 0.78, 1), shifting only `shiftHysteresis` (0.03) past an edge; in a gear the note is `shiftHertz` (140) × share / the gear's top, so it climbs and drops at each shift (to 91, 101, 110, 114 Hz), floored at `idleHertz` (50) plus `launchHertz` (30) × the driving pedal, capped at `maxHertz` (175, top gear past top speed). Reverse (`REVERSE_GEAR`, below -0.03 of top speed, kept until moving forwards) is one gear reaching 140 Hz at `reverseTop` (0.45, so about 155 Hz at half top speed, off the 175 Hz cap); backwards either pedal loads the engine (a wall bounce on full throttle leaves the car moving back; the throttle must not count as braking there); standing either pedal drives; forwards the throttle drives and the brake brakes. Level: `idleLevel` (0.45) + (`revLevel` (0.2) × revs × (`coastShare` 0.45 off the throttle, 1 on) + `loadLevel` (0.15) × drive) × (1 − `brakeCut` (0.4) × braking), so braking never goes under idle; cutoff the note × `coastBrightness` (5) to `loadBrightness` (9) with drive, inside `minCutoff` 900 – `maxCutoff` 5000 Hz; noise `noiseIdle` + `noiseLoad` × drive; wobble `wobbleCents` (20) at idle, gone by `wobbleFade` (0.25) of the rev range; the output is level × `gain` (0.3: peak about -13 dBFS into the limiter at volume 8, -10 at volume 10, room for the sounds still to come); `subMix` is 0.2 (the octave below sits near 25 Hz at idle, mostly cut by the high-pass). Measured on a rendered 20 s drive: idle through a 200 Hz high-pass (small speaker) 7 dB under full throttle through it, idle -30 dBFS RMS at volume 8. `main.ts` calls `engine.update` every frame (frame time, presentation): `driveEngine` glides every node with `setTargetAtTime` (`PITCH_SECONDS` 0.05, `LEVEL_SECONDS` 0.04, `CUTOFF_SECONDS` 0.05), nothing when the context isn't running. `engineHeard(state, raceLeft)` is when the car is drawn: the daily's pre-race screen, the race (countdown, fly camera too) and the results while the car rolls on (the daily's only with a race left); elsewhere (menu, settings, garage, loading) the level fades to 0 (`SILENCE_SECONDS` 0.12). The engine's numbers are `AudioTuning.engine` (`EngineTuning`), all on the Sound page. Tyres (`audio/tyres.ts`): `buildScreech` (10 nodes, from `createScreech` in `whenReady`, started once, never stopped, silence is level 0): 2 s of seeded looped noise (`noiseBuffer` in `audio.ts`) through three narrow band-passes (`q` 19): the note, `spread` (1.045) × it at `spreadMix` 0.7 (the two beat) and an octave up at `harmonicMix` 0.35, a sine LFO (`wobbleHertz` 6.5, `wobbleCents` 35) on their `detune` -> level -> high-pass (`highpassHertz` 200) -> the `world` bus. `screechSound(input, tuning, out)` is pure: from `slideSpeed(drawnCar)` (`render/drift.ts`, the drift sparks' measure; capped at the whole speed, so a standing car is silent) it is 0 up to `slideStart` (= `DRIFT_SLIDE_SPEED`, 2 m/s, so sound and sparks start together), then share ^ `fadeCurve` (1.5) up to full at `slideFull` (9 m/s); the note is `hertz` (1300) × (1 + `pitchRise` (0.25) × share), so 1300 to 1625 Hz. Braking in a straight line has no sideways speed, so it never screeches (there is no wheel lock). `main.ts` updates it every frame next to the engine with the same `engineHeard`; the level glides with `attackSeconds` (0.05) rising, `releaseSeconds` (0.1) falling, `SILENCE_SECONDS` when not heard, the pitch with `PITCH_SECONDS` (0.08); output `gain` 0.9 (its energy sits at 1.3-1.6 kHz where the ear is most sensitive: full screech -24.3 dBFS RMS, peaks -12.4 at volume 10, 1.6 dB under the engine's -22.7 RMS over a drive). Impacts (`audio/impacts.ts`): one thud per frame at most: `main.ts` keeps the hardest `Impact` of the frame's ticks and calls `thuds.hit(speed, normalX, normalZ, heard)` once after the tick loop (`crashDebris` still runs per tick). `thudSound(speed, tuning)` is pure: nothing below `minSpeed` (2 m/s, under the debris threshold of 3, so every hit that throws debris thuds and a 1 m/s nudge doesn't), level from `minLevel` (0.25) to 1 at `fullSpeed` (16 m/s), the body's start pitch `bodyStartHertz` (320 Hz, `bodyStartSoft` 0.25 lower on the softest hit), the crunch's mix (`crunchMix` 1, half on soft hits) and band (`crunchLowHertz` 700 to `crunchHighHertz` 2800, geometric). A thud is 5 nodes made for it (`NODES_PER_THUD`: a triangle dropping to `bodyEndHertz` 60 over `pitchSeconds` 0.12 with a 2 ms attack and an exponential decay to -60 dB at `bodySeconds` 0.32, plus the shared noise buffer through a band-pass decaying over `crunchSeconds` 0.12) into one permanent high-pass (`highpassHertz` 40) on the `world` bus, all released in the body's `onended`. `allowThud(gate, speed, normalX, normalZ, now, playing, tuning)` (pure, on `context.currentTime`): a hit at least `harderRatio` (1.5) times the last thud's speed always plays, inside the gap and at the cap (a faint 2 m/s contact must not hide the 13 m/s crash 17 ms later; the cap can be exceeded only by such hits, each 1.5 times the one before, so the stack is bounded by log1.5 of the speed range, about 7, and the sounds last 0.33 s); any other hit needs at least `minGapSeconds` (0.08) since the last thud and fewer than `maxPlaying` (3) sounding, and against the same wall (normals with a dot product above `sameWallDot` 0.7) it must beat the last thud's speed times `maskRatio` (1.15) faded by `exp(-since / maskSeconds)` (0.5 s) where `since` counts from the last contact with that wall, thud or refused, so an equal-speed or slowly falling stream (pushing along a wall gives an impact every tick) stays masked while the contact lasts and thuds once, and a hit on a clearly different wall (bouncing across an alley) is judged only by the gap and the cap. Each crunch starts at a random offset into the shared noise (`Math.random`, presentation), kept below the buffer's length minus the crunch's. Measured: a pinned car pushing on gives nothing after its first thud, a 5 s scrape one. Levels at volume 10 into the limiter: a 16 m/s thud peaks at -9 dBFS (-24 at 3 m/s); a 20 s scene of full throttle, drifts and hits peaks at -6.6 dBFS. Their numbers are `AudioTuning.tyres` (`TyreTuning`) and `AudioTuning.impacts` (`ImpactTuning`), all on the Sound page. Ambience (`audio/ambience.ts`): the city's hum, `buildAmbience` (from `createAmbience` in `whenReady`, all nodes `counted`, started once and never stopped; silence is level 0) on its own `ambience` bus (in `busGains`, so a slider): 16 s of seeded noise played by three looping sources, one over the whole buffer and two over its first 11.3 s and 7.7 s (`SHORT_LOOP_SECONDS`), so no cycle shorter than 16 s carries more than a third of the noise (envelope autocorrelation at the loop lags 0.1-0.25, against 0.9 for the old 5 s loop), through two band-passes, the rumble (`rumbleHertz` 140, Q 1.5, `rumbleMix` 3.5) and the air (`airHertz` 500, Q 0.8, `airMix` 0.07), plus three sines, a mains-like hum at `humHertz` 60 and its 2nd and 3rd harmonics (`humMix`, `harmonicMix` 0.04, the third half of that; 60, 120 and 180 Hz lie 10 Hz or more from every low harmonic of the engine's idle note, which `ambience.test.ts` keeps true, because tones near them beat against the idling engine), -> level -> high-pass (`highpassHertz` 40) -> the bus. Four sine LFOs of 13, 8.3, 21 and 29 s (`RUMBLE_PERIOD` ...) move the rumble's and air's levels, the air band's pitch (`sweepCents` 500) and the hum's level by `swell` (0.2), so it never settles into a static hiss. `ambienceHeard(state)` is every state except the garage (so the hum carries on through loading); `ambienceSound(input, tuning, out)` is pure: level (1 - `duck` (0.4) x share of top speed) x `carShare` (0.4) while the car is heard (`input.car`, `main.ts`'s `carHeard`), so the idling engine covers the hum and the engine and wind cover it more at speed; the level glides to `gain` (0.094) x that, or to 0 when not heard, with `fadeSeconds` (0.5), so screens don't cut. `main.ts` updates it every frame. Measured offline at volume 8 into the output (60 s render): the hum alone on the menu -38 dBFS RMS full range, -42 through a 24 dB/oct 200 Hz high-pass (4 dB under, so laptop speakers keep it), 39% of its A-weighted power above 1 kHz (was 87%), 72% of its power between 100 and 400 Hz (57% from the noise itself), the tones 4-8 dB under the noise in their band, slow level range about 8 dB over 60 s of 1 s levels; in a race at idle the hum is 9 dB under the idling engine both A-weighted and through the high-pass, and mixed with it adds no beating (the 100-200 Hz bands follow the hum alone within a few dB); garage -69 dBFS. Its numbers are `AudioTuning.ambience` (`AmbienceTuning`), all on the Sound page; `audio=debug` adds `ambience()`. URL parameter `audio=debug` puts `window.audioDebug` on the page (for headless checks): `stats()`, `waveform()` (the analyser's last window), `engine()` (the targets and their input), `screech()` (the same), `thuds()` (sounding, played since startup, and the impact speeds since the last call), `raceSounds()` (sounding, played, and a log of `{ kind, time (audio clock), tick }` since the last call) and `tuning`. Race sounds (`audio/raceSounds.ts`): four synthesised one-shots on the `interface` bus, `beep` (the countdown's 3, 2 and 1: one `baseHertz` 660 note, `beepSeconds` 0.16), `go` (`goOctaves` 1 above it, 1320 Hz, `goSeconds` 0.55), `checkpoint` (two notes at 3 × the base (`CHECKPOINT_OCTAVES`, a fifth above the go note, clear of the screech's 1.3-1.6 kHz) and a fifth up from that, 1980 then 2970 Hz, `checkpointGap` 0.075 apart, 0.18 each) and `finish` (660, 825, 990, 1320 Hz, `finishGap` 0.15 apart, the last `finishLastSeconds` 0.6, about 0.9 s to -40 dB). Each note is a sine plus a sine an octave up at `harmonicMix` 0.3 through an envelope (`attackSeconds` 0.008 linear, exponential decay to -60 dB at the note's length, then to 0), 4 `counted` nodes per note released in the fundamental's `onended`; all above the engine's 50-175 Hz. `raceSound(kind, tuning)` is the pure note table (hertz, start, seconds, level; nonsense tuning stays finite), `createRaceSounds(audio, tuning).play(kind)` returns the start on the audio clock or null (no context, suspended, clock not started, or every note's level 0; nothing is counted then). Triggers (`createRaceCues`, `observeRace(cues, race, tick, event)`, `takeCue`; pure): `main.ts` calls `observeRace` after every `stepWorld` and once after the frame's ticks (a race made by a state change shows its 3 before any tick runs), then `takeCue` once and plays it unless `document.hidden`, so a frame that ran several ticks plays one sound, never a burst. A beep is due when `countdownShown` changes to 3, 2 or 1, `go` / `gate` / `finish` come from `TickResult.race`; the latest cue wins except a `finish`, which nothing replaces and which is the only sound at the finish gate (no checkpoint with it). A different `Race` object (again, next, the daily, a new city) starts over; no race (free driving, menus, give up, results of a race that was cleared) gives nothing, and a beep already sounding finishes. Nothing is kept for later: a cue taken while the context is suspended or the tab hidden is dropped, and `gate=` / `car=` at startup make no event. Levels (`beepLevel` 0.17, `goLevel` 0.22, `checkpointLevel` 0.17, `finishLevel` 0.2, times the race `gain` 1 and the bus): alone at volume 10 the peaks are -14.4, -12.1, -14.3 and -12.8 dBFS; over a full-throttle drive the checkpoint's notes stand 11 to 25 dB over the engine plus screech within 10% of their pitch, and in 1-2.2 kHz 7 dB over at speed and about -3 dB in a full drift (the screech fills that band, 1.3-1.6 kHz, with peaks); the mix with the limiter peaks at -5.9 dBFS over a drift with a checkpoint (the drift alone peaks at -5.0 at its start). Their numbers are `AudioTuning.race` (`RaceSoundTuning`) with four `play` buttons on the Sound page.

- Input log and replay (`game/inputLog.ts`, `game/replay.ts`, pure, for the browser and a server): a log is one 5-bit code per tick (`inputCode` / `codeInput`: throttle, brake, steer + 1, drift; steer bits 3 is no input), only the keyboard's 24 combinations (an analogue value throws `InputLogError`, nothing is rounded), from the go tick (the first tick whose input is read) to the tick the finish is crossed in, so its length is the race time in ticks; at most `MAX_RUN_TICKS` (35 999, the timer's 9:59.983). `InputRecorder` keeps it as one byte per tick, growing by doubling. Packed (`encodeLog`, `decodeLog`): version byte (`INPUT_LOG_VERSION`), tick count as a LEB128 varint, then runs, a byte of code | (short << 5) for 1–7 ticks, short 7 plus a varint of length − 8 for longer; shortest varints, neighbouring runs different, nothing after, so a log has one encoding (at most `MAX_LOG_BYTES`, 36 003; a driven medium race about 2 KB). Text is base64url without padding (`encodeLogText`, `decodeLogText`, hand-written, no `Buffer` or `btoa`). Decoding returns `{ ok, log }` or `{ ok: false, fault }` for any bytes or text, checks sizes before allocating, and rejects unknown versions, truncation, trailing bytes, runs past the tick count, codes no input has and non-canonical forms. `replayInWorld(world, log)` runs a world whose race is in its countdown through the countdown and the log: `finished` with the ticks and gates only if the finish is crossed on the log's last tick, else `logEnded` or `inputsAfterFinish`; `replayRun(citySettings, carSettings, routeSeed, routeOptions, log)` does it in a fresh world without vertices (about 30 ms for a medium race in Node), `replayDaily(day, log)` on the day's city and route. `replay.test.ts` replays the driver test's 16 races (keys) to their live finish, and the same log started at tick 12 345 after the menu in a world with vertices, and again after driving on past the finish, gives the same car bit for bit; it stores the hash of one packed race (`PACKED_RACE_HASH`). `main.ts` records every race's inputs on the ticks it reads them (a new `Race` object starts a new log), and at the finish, in dev builds or with `replay=1`, packs, unpacks and replays it (applying `gate=` / `car=` again when the race was started with them) and logs both finish ticks.

the daily states work only under `shot` (or `tick`), elsewhere they open the menu; under `shot` the clock is pinned `next=SECONDS` (default 5:12:44) before the day after `day=` (day 0 without it); `board=N` with `state=dailyresults` shows a made-up board instead of the server's (`dev/sampleBoard.ts`: `sampleBoard(day, N, ownTicks, nickname)`, N runs seeded by the day, 82 s ± 7 with a slow tail, made-up nicknames, the player's run among them when finished, answered exactly as `daily_results` would); `scripts/shots.mjs` passes `state=race` unless a shot names another), `seed`, `blocks` (blocks per side, 3 to 14, the dev menu's range: another city size; not with the daily states), `day` (start in that day's daily city, negative allowed; `seed` wins; without either the city is today's), `mode` (a `RenderMode` name, any case), `camera=x,y,z,yaw,pitch` (degrees; switches to the fly camera), `tick=N`, `shot`, `hud=test` (the text layer's test card), `cell=N` (cell width in CSS px, the dev menu's range) `entry=N` (the menu entry selected at the start, 0 to 5; with `state=results` the finish screen's option, 0 to 2; with `state=settings` the row, 0 to 4; with `state=garage` the row, 0 to 1) `edit=TEXT` (with `state=settings`: the nickname being typed, up to 12 letters, digits or spaces), `shape=` and `color=` (a `CAR_SHAPES` / `CAR_COLORS` id: the car instead of the stored one, in any state; saved with the next settings change unless under `shot`). Nothing random runs under these parameters: unlimited picks a random city only when a player chooses it. With `tick` the world is stepped to that tick with no input at startup and then held: the clock never runs and `dt` is 0, so signals, beacons, neon and water are the same every load. Once a frame of the frame loop has been drawn (never the startup loading frame) the canvas gets `data-ready="true"`, which `scripts/shots.mjs` waits for. Two runs of `npm run shots` give byte-identical PNGs. `drive=1` makes the held tick's stepping hold full throttle instead of no input, so shots show the car at speed. `replay=1` replays every finished race headless at the finish and logs `replay: finish tick live N vs replay N` to the console (always on in dev builds).

### City generation (`game/city.ts`)

The city is plain data (rectangles and zones) with no WebGL in it. The renderer, collisions and a future server all read the same data. Units are metres.

- **Grid**: 8×8 blocks of 60 m, 12 m roads, a road around the outside too. Centred on the origin; the middle junction is only exactly on it when the avenues are spread evenly. The 60 m block size is fixed: low and mid density lots are shares of the block, so a different size would stretch every building and break models designed for the lots.
- **Avenues**: some road lines are 20 m, 4-lane avenues: one through downtown each way, plus extra avenues with `avenueDensity`, less likely by `AVENUE_FALLOFF` per road line further out. Never the outer ring. Streets get a dashed centre line; avenues a solid centre line and a dashed divider in each half.
- **Junctions** (`city.junctions`, row by row): each has a `control`, and per leg (the road leading in) whether its traffic `stops` and whether it has a crosswalk. Lights where an avenue crosses; nothing at the ring's corners; two-way stops where streets meet the ring (the ring drives through); all-way stops where 2+ corner blocks are busy (mid density, high-rise, plaza, supermarket); other street crossings are two-way stops where the road nearer a downtown avenue drives through. Crosswalks only on legs that stop, and only at lights or with a busy corner.
- **Ground**: roads are dark grey, so they show as dim glyphs and the white dashed centre lines stand out. Lines are 0.4 m wide (real paint is ~0.12 m) so they cover a cell at a distance, and dashes stop short of junctions. Pavements are raised 0.15 m so curbs give each block an outline.
- **Zoning**, in this order:
  1. Downtown gradient: a seeded centre near the middle (`DOWNTOWN_OFFSET`); each block's mid density chance slides from 0.9 at the centre to 0.1 at `DOWNTOWN_RADIUS`. Distances are in blocks, not metres.
  2. Neighbour rules (N/E/S/W only, edge blocks have fewer): mid density with 3+ mid density neighbours becomes high-rise; then low density with 3+ low density neighbours becomes houses, unless it shares a side with a high-rise (diagonals across a crossing are fine); those stay shops as a buffer. These read a copy of the original zones so the order blocks are checked in doesn't matter.
  3. Plaza: at most one, a random high-rise whose 4 neighbours are all high-rises. Breaks up walls of towers.
  4. Specials: 1 park and the supermarket replace random low density blocks, the parking lot a random mid density block. Skipped if no candidate exists.
- **What zones mean**: low density = shops and low-rise, mid density = mid-rise, high-rise = towers, houses = 4 per block, set in towards the block centre with their yards facing the street, separated by fences (`game/fences.ts`, darkest area at night). Park, plaza and parking lot are open ground.
- **Outer wall**: a continuous ring of buildings one block deep around the outer road, so every street dead-ends at a building and the city seems to carry on. It is the boundary; `bounds` is the drivable area inside it.
  - Set back 3 m (`WALL_SETBACK`) behind a pavement ring (`wallPavement`), like the blocks. Corners are the remaining squares (57×57 m).
  - Each side (594 m by default) is made of fixed-width pieces so prefab designs fit: 21, 28 and 35 m (3, 4 and 5 units of `WALL_UNIT` = 7 m), plus one flex piece that takes the remainder.
  - Counts: units = floor(side / 7), minus one if the remainder is under `FLEX_MIN_WIDTH` (7 m), so the flex piece is always 7–13 m. Equal sets of the three widths (12 units each), then `WALL_EXTRAS` fills the leftover units (1 and 2 borrow a set). Works for any side of at least 84 m. Default: 7×21, 8×28, 6×35 and a 13 m flex.
  - Every side uses the same pieces in its own shuffled order (`shuffle`, Fisher-Yates, seeded with `blockSeed(seed, blocks + side)`), so the wall doesn't mirror the street grid. The flex piece is shuffled in like the others.
  - The flex piece stays open as an alley, gated at its mouth (see Flex alleys).
- **Buildings** (`game/buildings.ts`, roadmap steps 7 and 11): `generateBuildings(city, settings)` turns each block into a list of `Building`s (footprint `rect`, `base`, `floors`, `floorHeight`, `height`), using a per-block generator (`blockSeed`). A `Record<Zone, BlockBuilder>` table picks the builder, so a new zone won't compile without one. Blocks are inset 3 m from the curb (`inset`), and `split` cuts them into lots, touching or with 4 m alleys (`ALLEY_WIDTH`) between columns and rows. Probabilities live in `CitySettings` so the dev menu can change them. Heights come from a `FloorPlan` per kind of building: `height = base + floors × floorHeight`, the floor height picked from a short list, whole floors from a range, `base` a raised ground floor (houses only). `storeys(plan, random)` rolls one. The dev menu's per-zone sliders scale the floor count (rounded, at least 1) and one ceiling slider scales every floor height, both after generation so the random calls don't change. Every roll happens whatever the outcome, so one result never shifts the next.
  - Low density: up to 8 touching shops (3×3 lots, centre lot empty as a back yard), floor heights 6/7/8 m, 1–2 floors (`SHOP`). Each lot is left empty with `lowDensityEmptyChance` (1 in 16), for a small car park later. Then a side's middle shop can merge with each of its corners (`lowDensityMergeChance`, 0.4) into one building, if both lots have a shop; each corner joins at most one side (sides checked in a fixed order), so merged shops stay rectangles. Merged shops are 1–3 floors (`MERGED_SHOP`). A block is a strip mall with `lowDensityStripMallChance` (0.1): a random corner and its two neighbouring lots (0-1-3, 1-2-5, 5-7-8 or 3-6-7) become its car park, the other shops are never left empty, and every shop is 1 floor (`STRIP_MALL_SHOP`).
  - Fillers: `Filler`s fill one lot and return a layout (`mall`, `midRise`, `lowRises`, `seating`, `towerIn`), so zones can mix them.
  - Mid density: 2×2 mid-rises, floor heights 3/3.5 m, 5–10 floors. Alleys north-south and east-west are rolled separately (`midDensityAlleyChance`, 0.5), so a block gets none, one direction or both. Touching neighbours merge with `midDensityMergeChance` (0.35) into one building of 8–14 floors (`MERGED_MID_RISE`); each lot joins at most one.
  - High-rise: floor heights 3.5/4 m, 15–40 floors. Weighted layouts (`HIGH_RISE_LAYOUTS`): one tower at 50–70% of the block; one big building with 5 m sidewalks; a tower on one quarter with fillers on the rest (`TOWER_NEIGHBOURS`); two towers on opposite corners with alleys between, seating on the other quarters.
  - Houses: 4, one per quarter (index 0 north-west, 1 north-east, 2 south-west, 3 south-east), each grown from the corner nearest the block centre with a 2 m gap to the centre lines (`HOUSE_FENCE_GAP`) for the fence. Floor heights 3.4/3.7/4 m on a 0.5–1.2 m base, 1 floor, 2 with `HOUSE_TWO_STOREY_CHANCE` (0.15). Houses have `kind: 'house'`, garages `kind: 'garage'` (only houses get pitched roofs), and both carry `entrance`: the street side (`Side`) the lot opens to and the garage door faces, for driveways.
    - Shape: the core is a 10–13 m square (`HOUSE_SIZE`); with `WIDE_HOUSE_CHANCE` (0.5) it is a wide house instead, 16–20 × 9–11 m along either street. A square house's entrance is either street, a wide house's the street along its long wall.
    - Garage: with `housesGarageChance` (0.5), a square box 6–7 m (`GARAGE_WIDTH`), 3.7 m tall, against the entrance wall (`attached()`) at one end or the middle (`GARAGE_SPOTS`).
    - Big house: two neighbours across a centre line (`HOUSE_PAIRS`, each with the street the pair shares) join with `housesBigHouseChance` (0.15) into one big house, the box around their two cores, always 2 floors, entrance on the shared street. Each house joins at most one. Garage with `BIG_HOUSE_GARAGE_CHANCE` (0.8), 8–9 m square, in one of 4 equal spots: on either end wall flush with the front, or on the front wall at either end.
  - Supermarket: one box (floor height 6/7/8 m, 1 floor) on the half of the block away from a random street; the other half is its car park.
  - Park, plaza, parking lot: none.
  - Wall pieces: one building filling the whole piece, so neighbours touch, floor heights 3/3.5 m, 3–10 floors (`WALL`, narrow pieces `NARROW_WALL` 5–9). Own plans, separate from the zones, so game modes can change them. Flex pieces get none.
- **Fences** (`game/fences.ts`): `houseFences(city, buildings)` runs after the buildings, so it knows about big houses and entrances. Per houses block: a post at the centre and four arms out to the sidewalk between neighbouring lots; an arm that runs into a building (a big house) is left out. Each lot (its quarter, or half for a big house) is also fenced where grass meets sidewalk, except on its entrance side; edges stop at the arms so nothing overlaps. 0.3 m thick, 1.8 m tall (`FENCE_THICKNESS`, `FENCE_HEIGHT`), solid (`cityColliders`), one mesh.
- Batching: everything on the lots is one mesh built once with corners already in world position, drawn in a single call. Pavements and wall slabs are one mesh each too.
- Models (`render/models/`): a `BuildingModel` is a function of (building, random) giving a `Model`: vertices plus its own colliders, so a stepped tower is only solid where it stands. Models are plain numbers with no WebGL. `model.ts` has `faceOf`, one wall in its own coordinates (u along, y up, w out). `spawn.ts` holds the rules: `RULES` gives each `BuildingKind` weighted styles, where a weight is a function of the building (avenue frontage, neighbourhood, size; 0 = never), and `cityModels` builds everything. Each building, open lot, yard and flex alley has its own generator (seeds from `MODEL_SEED` etc.), so what is drawn never changes the layout. Styles: shops (`neonShop`, `sleepyShop`), mid-rises (`brickWalkup`, `concreteFlats`, `steppedFlats`, `hotel`, `wallBlock`), towers (`glassSlab`, `steppedDeco`, `podiumTower`, `twinSlab`), `mall`, `superstore`, `house`, `garage`.
- Colours (`render/models/palettes.ts`): a hand-picked palette per style; keep brightness similar within a palette so the glyphs stay the same. `neonFamily` gives a neighbourhood three neon colours in a row.
- Neighbourhoods: `Building.neighbourhood` (0–1) is shared by blocks in the same `NEIGHBOURHOOD_BLOCKS` square, so styles and neon cluster. `Building.avenues` lists the street sides that face an avenue.
- Neon (`render/models/neon.ts`): a 5×7 font drawn with `pixelArt` in the animated `neon` set; `neonText`, `neonStack` (blade signs) and `neonTube`. A sign's board glows faintly in its colour (`SIGN_GLOW`), so it still reads as a patch of colour where the letters are smaller than a cell. All sign words (`buildings/signs.ts`) are made up and use only letters the font has.
- Open lots: `generateBuildings` returns a `Layout`: `buildings` and `open` (`OpenLot`: use `yard`, `parking`, `seating`, `plaza`, `park` or `alley`). `props/openLots.ts` furnishes each use with the prefabs in `props/props.ts` (tree, bench, planter, bollard, dumpster, parked car, fountain, kiosk). Car parks: aisles run in from `entrance`, the middle one on the sidewalk's gap. Lots with an entrance are at road level, the others on the pavement. Yard trees keep clear of house and garage colliders (porches too), driveways and fences; park trees of paths, pond, kiosk and each other; an alley's dumpster stays out of the middle fifth, where a crossing alley may run.
- Flex alleys: a barred gate across the mouth and a blank wall behind it, both solid, with a dumpster between.
- Glowing things still light nothing around them; only headlights do.
- Street sides: every block building carries `streets`, the sides that lie on the edge of the block's lot area (the block inset by `SETBACK`), found by geometry after the builder runs: 1 for a middle lot, 2 for a corner, 0 for set-in buildings (houses, towers). Wall side pieces face the city (`wallStreet`), corner pieces nothing (they only touch the pavement at a point). Models will pick their design from it.
- **Street lights** (`game/streetLights.ts`): placed per road segment (between two intersections), on the pavement 1 m from the curb, if the block beside it is low density, mid density or high-rise. Spaced by `streetLightSpacing` (25 m) between `CORNER_CLEARANCE` (8 m) at each end, kept free for traffic lights and stop signs; when both sides are lit they alternate sides. Each light is a position plus the direction its arm faces. The model (pole, slanted arm, head, glowing bulb) is in `render/models/street/streetLight.ts`, all lights in one mesh.
- **Intersections** (`game/intersections.ts`): traffic lights and stop signs from the junction data, as plain data. Corners are written as signs (±1 in x, ±1 in z); poles stand 1 m in from both curbs. Traffic lights stand on the far right corner of the leg they control (US style), so each corner serves one leg, with the arm reaching back over that traffic's lanes: 2 heads over the lane centres on an avenue, 1 over the centre line on a street. Crosswalk lights (Vancouver style: walking person and hand in one spot) go on the poles at both ends of each crosswalk, on a short pole where a corner has no traffic light. Stop signs stand on the near right corner, just before the crosswalk (`CROSSWALK_LENGTH` is shared with `city.ts`). A stop sign's position is its pole; the plate hangs in front.
- **Signals** (`game/signals.ts`): `signalPhase(tick, offset)` is a pure integer function: a 48 s cycle per junction (column road green with walking person then flashing hand, yellow, all red, then the same for the row road; the hand flashes 0.5 s on, 0.5 s off). `signalOffsets` gives each junction an offset: green waves along avenues at `WAVE_SPEED` (50 km/h) in a seeded direction with a seeded start (the column avenue wins where two cross), seeded random offsets elsewhere. Its generator is `blockSeed(seed, SIGNAL_SEED_INDEX)`, separate from the rest of the city.
- **Road graph** (`game/roadGraph.ts`, `world.roadGraph`): `roadGraph(city)` gives plain data for routes, built without randomness. Nodes are the junctions (index into `city.junctions`, row, column, x, z). Segments are the stretches between neighbouring junctions, ring included, numbered row by row (at each node the east one, then the south one); `a` is the west or north end, `b` the east or south end, with axis, length between centres, width and avenue flag (read from the blocks' gaps and the bounds, so it needs no settings), the centre line's ends and `clearStart`/`clearEnd`/`clearLength`, the stretch between the two junction squares. `links[node]` lists each node's segments with the node at the far end, always in north, east, south, west order (`LEG_ORDER`). Helpers: `otherEnd`, `directionFrom`, `pointAlong`, `turnBetween` (straight, left, right, uTurn through a shared node; Z grows south, so left from north is west). It is not part of `cityDigest`.
- **Routes** (`game/route.ts`): `generateRoute(graph, seed, { length })` gives plain data: `legs` (segment, from, to, direction, turn into it, ring and avenue flags), `junctions` passed, the `start` line, the car's `pose` (`START_POSE_BEHIND` behind the line, heading a whole number of quarter turns so `sin`/`cos` are exact), `gates` (checkpoints in order, the finish last: leg, segment, centre-line point, travel direction, road width, distance along the route), `length` and a `polyline` (start, every junction, finish). Its generator is `blockSeed(seed, ROUTE_SEED_INDEX + attempt)`, separate from the city's. The path is a depth-first walk from a random segment off the ring in a random direction: each junction's ways out are ordered by weighted draws (`STRAIGHT_WEIGHT` 8, `TURN_WEIGHT` 1 each side, times `RING_WEIGHT` on the ring, at most `MAX_RING_RUN` ring segments in a row; times `REPEAT_TURN_WEIGHT` 0.02 for a way that turns the same way as the junction before, now or unavoidably within `FORCED_DEPTH` junctions, as at a ring corner or the end of a ring run, so loops round a single block are occasional), a segment is never used twice (so no U-turns), junctions may repeat (the route may cross itself), and it backtracks when stuck or overshooting. It stops at the first leg on which start and finish fit strictly inside their ranges for the target length (start line with `START_GRID_LENGTH` of clear stretch behind it and `START_LINE_MARGIN` 20 m ahead, finish `FINISH_MARGIN` 20 m from the junction squares, so it isn't crossed still cornering; a segment too short for the finish range is only driven through); the start position is rolled within what hits the target exactly. A search runs out after `SEARCH_STEPS`, then a new attempt; only if no attempt hits the target strictly is the first attempt's best effort used (start and finish at the ends of their ranges, or the nearest length within `ROUTE_LENGTH_TOLERANCE` above); a city whose roads are too short or that never fits throws `RouteError`. Gates stand mid clear stretch on every leg turned into and on straights where the next gate spot would be more than `GATE_SPACING` away. Lengths: `ROUTE_LENGTHS` short 1250, medium 1800 (`ROUTE_LENGTH`), long 2500 m, tuned with the test driver (`npm run drive`): it takes medium routes in 70–94 s, a drifting player should be 10–20% faster. `route.test.ts` checks 1000 routes (250 cities × 4 seeds) plus 6×6 and 10×10 cities at every length, and stores digests of three routes (`REFERENCE_ROUTES`).
- **Race state** (`game/race.ts`, `world.race`): `null` is free driving, exactly as before races existed. `startRace(world, route)` works at any tick: the car goes to the route's `pose` standing still (`previousCar` too, so nothing is drawn between) and a `Race` starts in `countdown` with its `startTick`; `createRaceWorld(city, car, routeSeed, options)` starts one at tick 0 (throws `RouteError`), `clearRace` goes back to free driving. A `Race` is the shared, never-changed `route` plus plain numbers (`phase`, `startTick`, `nextGate`, `finishTick`, -1 before), so rollback copies it with a spread. Only `stepWorld` advances it: for `COUNTDOWN_TICKS` (3 s) the car isn't stepped and the input isn't read, then `running` from the go tick (`goTick`), `finished` once the last gate (the finish) is crossed; after that the time is frozen and the car drives on. A gate counts when the car's centre moves (from before the step to after collisions) from strictly behind its line to on or past it, within the road plus `GATE_SPAN_MARGIN` (`SETBACK`, the pavement) each side, read where the path meets the line; only `nextGate` is tested, so backwards and out-of-order crossings do nothing and a bounce on the line can't count twice. Time is whole ticks from the go tick to the tick after the finishing step (`raceTicks`); `formatRaceTime` gives m:ss.mmm with milliseconds rounded down, in integer maths. `countdownShown(race, tick)` gives 3, 2, 1, 0 for go (`GO_SHOWN_TICKS`), else null. `TickResult.race` reports that tick's event (`go`, `gate` with its index, `finish` with the time) for the renderer and sound; nothing in the simulation reads it. `runReference` hashes the race state (`hashRace`) and events only when there is a race, so free-driving hashes are unchanged. The game states (below) start races: unlimited on a random city's route, the URL's `state=race` on the city seed's (route seed = city seed, default length both); the URL parameter `race=0` makes the race state drive freely from the middle junction instead, which every shot from before races uses (the car and its headlights show in fly shots too).
- **Test driver** (`game/driver.ts`): `driverInput(world, state)` gives one tick's `CarInput` from the world and a small `DriverState`, in plain numbers and `math/deterministic.ts` only, so a driven race is reproducible. It follows the route's polyline down the centre lines: steers at a point `LOOKAHEAD` + `LOOKAHEAD_TIME` × speed ahead (the car turns at most 0.6 rad/s gripping, so the aim must start a turn about a turning radius early), full throttle on straights, brakes (planning `BRAKE_PLANNING` m/s²) to `CORNER_SPEED` 10 m/s (`AVENUE_CORNER_SPEED` 12 between avenues) by `BRAKE_EARLY` before each turn, never drifts. It never moves on past the next gate's leg; past a gate's line without it counting it goes back behind it; far off the line (`OFF_ROUTE`) it heads straight back to it; stalled (`STALL_TICKS` under `STALL_SPEED`) it backs out, longer each time in a row; standing facing away from the aim it backs round first (a K-turn with the stall rule). `driveRace(world, maxTicks, keys)` drives until the finish (with `keys` the steering is tapped full lock or none each tick, the difference carried over, so every input is a keyboard one and can be logged) and returns the result with every input, one per tick from the call, countdown included: the first full recorded races. `driver.test.ts` drives 16 races (default city, short, medium and long, a 6×6 and a 10×10 city) to the finish at a good pace with every gate in order and no back-outs, the car turned backwards or towards the kerb at go, replays the recorded inputs in a new world to the same finish tick, and stores the hash of one complete driven race (`DRIVEN_RACE_HASH`, from `runReference`). `npm run drive -- first last [--length name] [--blocks N]` (`scripts/drive.ts`, Node runs the TypeScript directly) sweeps many seeds and prints finish rate, times, average speed, impacts, back-outs, the slowest and failed seeds. `createWorld` / `createRaceWorld` take `vertices = false` for a world without drawn vertices (same simulation, much faster).
- **Gates** (`render/models/gate.ts`): an arch per gate of the race's route: two glowing posts at the kerb side of the pavement (`POST_FROM_CURB` 0.8 m, about the street-light pole line, clear of awnings and canopies; a crossing still counts out to the building line) and a header 8.5–13.5 m up, above the street lights. Only the header's side facing the approaching car has a lit panel, so the gate shows the way; checkpoints are lime (`CHECKPOINT_COLOR`), the finish a white chequer (`FINISH_COLOR`). Lit parts use the steady `gate` set, not the animated `neon` one, so a gate doesn't read as a sign. Above the header a 6 m wide beam rises to `BEAM_TOP` (50 m) in the `gateBeam` set (the finish's pink-white, `FINISH_BEAM_COLOR`): the marker that finds the next gate down the road, about 4 columns × 9 rows at 250 m. The vertex shader fades it from `BEAM_NEAR_GLOW` inside `BEAM_FADE_NEAR` (60 m) to full beyond `BEAM_FADE_FAR` (150 m), so close up it is a faint column. The next gate's glow breathes between `GATE_PULSE_MIN` (0.7) and full over `GATE_PULSE_TICKS` (2 s), brightest on whole cycles, from `u_gatePulse` that `main.ts` derives from the tick (shots use tick 120). Not solid: no colliders, nothing in the simulation changes. All gates of a route are one mesh, rebuilt in `main.ts` whenever `world.race.route` changes (none in free driving); each gate's vertices carry `gateId(index)` = `GATE_ID_BASE` (-10) minus the index, its beam `beamId(index)`, `BEAM_ID_OFFSET` (1000) further down, and the vertex shader compares the index with `u_nextGate` (`race.nextGate`): passed gates are clipped away, the next glows with its beam, later ones are unlit (`UPCOMING_GATE_DIM`, no emission) and their beams clipped. After the finish `nextGate` is past the last gate, so all are gone. The URL parameter `gate=N` sets the race's next gate at startup, for screenshots. A street light can stand inside a finish gate's post (the finish is anywhere on its leg); its pole hides in the post and its arm comes out of it.
- **Signal rendering**: lamp and walk symbol vertices are built lit and tagged with `id = junction * 10 + road * 5 + lamp` (road 0 column, 1 row; lamps red, yellow, green, walking person, hand). Every frame `render/signalTexture.ts` uploads one RGBA8UI texel per junction (road lights and walk lights) and the scene vertex shader dims lamps that are off and clips the walk symbol that is off, so the mesh is never rebuilt. The tick itself never goes to the GPU (floats lose whole numbers past ~77 hours of ticks).
- Ground surfaces (`ZONE_SURFACES` in `main.ts`): each zone's material and colour. Concrete for shops, mid-rise, towers and plaza, grass for houses (inside a concrete sidewalk `SETBACK` wide) and park. Curb sides are concrete grey (`withSideColor`). Supermarket and parking lot are lots (`game/lots.ts`): only a sidewalk ring with an 11 m entrance gap is raised, plus the supermarket's store half; inside, the road slab shows at road level. Parking lot entrances face the city centre, supermarket entrances the car park side.
- Particles (`render/particles.ts`, `particle.*.glsl`): visual only, stepped with frame time and drawn as 1-pixel GL points after the car, so each is one glyph; they fade as they age, so the glyph walks down the `debris` ramp. One dynamic buffer sized for `MAX_PARTICLES`, overwritten with `bufferSubData` each frame. Each particle has a `ParticleKind` (colour, material, life, spread, gravity, drag); the material is in the vertex data. `collideCar` returns an `Impact` (speed into the wall, wall normal); hits above `DEBRIS_MIN_SPEED` throw debris off the wall (`crashDebris` in `main.ts`).
- Drift particles (`driftParticles` in `main.ts`, wheel positions and slide speed in `render/drift.ts`): while the car slides sideways faster than `DRIFT_SLIDE_SPEED`, each tick bursts `driftSpark` particles upwards from the bottom of each rear tyre, more and faster the harder the slide. Tire marks were tried and dropped: a persistent trail per car is too much to track for multiple players.
- A pond (`flatDisc`, animated `water` set) sits in the middle of the park; `POND_RADIUS` is in `game/park.ts`, so the trees keep clear of it.

### Known limits

- Anything thinner than a cell (lines, thin poles) can vanish or flicker. Prefer filled surfaces over `gl.LINES`, and make thin real-world things chunky (hedges instead of wire fences, thick poles, big sign faces).
- Flat details (markings, pixel letters, sign layers) sit 2 cm in front of their surface. With the 0.5 m near plane, depth precision is ~3 cm at 500 m, so they could fight beyond ~400 m, where they are smaller than a cell anyway.
- Headless Chrome (SwiftShader) drops lines that cross behind the camera; real GPUs draw them. Only matters for headless screenshots.

## Roadmap

The finished game is described in `SPEC.md`. The steps and their sub-steps are the checkboxes in `README.md`; that list is the task queue.

## Conventions

- Strict TypeScript. No `any` unless unavoidable and commented.
- Keep the simulation deterministic: fixed timestep for physics, separate from the render frame rate. Game state must be reproducible from inputs alone (needed for ghosts and rollback).
- Simulation code must give identical results in every browser. `Math.sin`, `Math.cos` etc. can differ between browsers, so the simulation will need its own deterministic versions before multiplayer. Rendering can use `Math` freely.
- The game client stays a static site (any static host works). Only multiplayer needs a server.
- Generation is seeded (`math/random.ts`, Mulberry32), never `Math.random()`. A seed is the city's ID: same seed, same city for every player. Results depend on the order of `random()` calls, so from roadmap step 7 on each block gets its own generator from the city seed and the block index (zoning uses one city-wide generator); adding a random call in one place then doesn't reshuffle the rest of the city.
- Open numbers (thresholds, sizes, counts) are named constants with a sensible default, tuned as we go; later exposed as dev menu sliders. Don't block on choosing them.
- Judge the look in glyph mode (and grey levels for whether shapes read), from driving height (~1.2 m). Full resolution mode is only for debugging geometry. Glyph choice follows brightness only and the glyph takes the cell's true colour, so brightness separates shapes.
- Detail smaller than ~1 m disappears beyond ~40 m (about 8 cells per metre at 20 m, 2 at 80 m). Buildings read by silhouette and height.
- Shaders live in `.glsl` files and are imported with Vite's `?raw` suffix.
- Keep comments to a minimal neccesary use
- Commit after each small working step, in the style of the existing history: `Topic: what changed`, no prefixes like `feat:`.
- One branch per roadmap step, named like the existing ones (`fly-camera`, `visual-identity`), merged into `main` with a pull request titled `Step N: Name`. Tick sub-steps in `README.md` as they are done.
- Dev dependencies are fine (Vitest, Playwright, the Supabase CLI). Runtime dependencies are not, except `@supabase/supabase-js`.

## Building with /go

The owner has made the creative decisions (`SPEC.md`) and is usually away. `/go` (`.claude/skills/go`) in a Claude Code session on the owner's Mac starts the build; the session's model is the lead and stays the lead until the owner says stop. State lives in the repository (`README.md` checkboxes, `PROGRESS.md`, git), so a new `/go` carries on where the last one ended.

### The lead

The lead plans, delegates, reviews and commits. It does not write features itself, so its own context stays small enough to run for hours.

For each sub-step, in roadmap order (first unticked, unblocked sub-step of the first unfinished step, on that step's branch):

1. Brief the `builder` subagent (`.claude/agents/builder.md` holds its standing rules). The brief stands alone: the sub-step, the part of `SPEC.md` it serves, the files to read first, what done means and how to prove it. It runs on `sonnet`; pass `model: opus` for the hard parts (simulation changes, shaders, netcode, anything a first try got wrong). Use `Explore` for searching. A sub-step too big for one brief is split in the README first.
2. One builder writes in the working tree at a time. Other subagents may run alongside only if they read (research, review, looking at screenshots).
3. When it reports back, have the `reviewer` subagent look at the uncommitted work; it has not seen how it was written. Then check yourself: `npm run check`, and for anything visible `npm run shots` and look at the pictures in glyph mode. A `fix` verdict or a failed check goes back to a builder with the findings. Twice failed: discard the changes and mark the sub-step blocked.
4. Tick the sub-step, update the "How it works today" notes above if how something works changed, add the entry to `PROGRESS.md`, commit, push.
5. When every sub-step of a step is ticked: tick the step, open the pull request (`Step N: Name`, a few bullets of what was built and how it was checked), wait for CI, merge with a merge commit, keep the branch, start the next step's branch from `main`.

While `.claude/go.active` exists (made by `/go`, removed by `/stop`) a Stop hook (`.claude/hooks/keep-going.sh`) counts the unticked, unblocked sub-steps and sends you back to work if any remain. When you have to end a turn anyway (waiting for a background subagent, or the owner wants you to hold), `touch .claude/go.pause` first and remove it when you resume. After the context is summarised, another hook prints the end of `PROGRESS.md`.

Other rules:

- `main` only changes through pull requests with green CI.
- Stuck, or something only the owner can do (an account, a secret): add `  - blocked: reason` under the sub-step, note it in `PROGRESS.md`, go on with the next sub-step that doesn't depend on it.
- A decision the spec doesn't cover: pick the simplest thing, add a line to "Decisions made along the way" in `SPEC.md`.
- A bug found on the way: fix it if small, otherwise add a sub-step.
- Things tried and dropped are written down above with the reason.
- When every step is ticked: play through every mode against `SPEC.md` (headless runs, screenshots), fix what turns up, then stop and say so.

### When the owner speaks

Any message from the owner while building ("hey im back", a question, a change) gets answered first: what was finished since they left, what is running now, anything blocked or worth their eyes, from `PROGRESS.md` and the running subagents. A running subagent carries on unless the message means its work is wrong. Then do what they ask:

- A change to the game: edit `SPEC.md` and the roadmap first, then build it.
- Screenshots: `npm run shots` (or a one-off picture of what they name) and open them with `open`.
- "go" or nothing more: carry on.

### When the owner says stop

`/stop`, or "stop" in words: let a subagent that is nearly done finish and commit its work if it passes; stop the others and discard their half-done changes (say what was dropped in `PROGRESS.md`). Leave the tree clean and pushed, stop `caffeinate`, and give a short summary: done, in what state, next.
